Board Game Curator Architecture

A static web page talks to one small API service on a small server. The API (api.ondorilabo.com) answers what the page asks for: shelves, friends, wishlists, profiles, rulebooks, the admin portal, and Nathan, the curator, who streams his answers as he writes. A second copy of the same code, the jobs worker, runs the scheduled jobs and the long ones: nightly play syncs, the self-test, the rulebook reader, imports, filling the catalog. Both use one Postgres database and call out to Google, BoardGameGeek and AI models. n8n is still on the server, but only as a fallback the page can fall back to; nothing runs there on a schedule any more. Every member's shelf, Dan's included, takes the same path.

What happens when someone taps something

Every action on the page follows the same path, whether it's rating a game, adding one, or opening a friend's shelf.

  1. The page signs you in with Googlebrowser · Google's own account chooser ("Continue as…"), with a "Sign in with Google" button as a fallbackOne click, or none when the browser remembers you. It keeps the Google ID token in the browser and sends it with each request.
  2. Cloudflare passes the request to the APIapi.ondorilabo.com/vault/…The server has no open ports. The Cloudflare tunnel is the only way in. Each area of the site has a switch in Admin, and every area is on. If the API ever can't answer, the page asks n8n (n8n.ondorilabo.com/webhook/vault/…) instead, until those webhooks are retired.
  3. The API checks who you areGoogle's public keys (cached) → bgc.sign_in(email)The token must be signed by Google for our site and not expired, and your email must belong to a member. The result says your role (member or admin) and which shelf is yours. Then a per-member rate limit, and the inputs are checked.
  4. The route does the work in the databaseone SQL function call, e.g. bgc.shelf_view, bgc.rate, bgc.wish_changeThe same functions the jobs worker calls, so the rules are the same either way, and the same ones for Dan as for every member: only admin vs member differs. Privacy rules live in the database. A friend's shelf, wishlist or profile only comes back if you're connected by friend code.
  5. The page redrawsJSON back to index.htmlErrors come back as a plain message, and the badge at the top shows "Signed out" when your sign-in has expired.

How Nathan answers a question

Nathan runs in the API, and his words stream to the page as he writes (first words in about 2 seconds, the whole answer in about 5). His steps are n8n's own code, copied word for word from the Ask workflow in n8n/gen.js, so the two can't drift apart; n8n's Ask is the fallback until about November 6. Two AI steps do the reading and the writing. Plain code and SQL around them decide what's true: which games exist, who owns them, and what fits the limits.

  1. Database
    Count the question. Each member gets 30 a day (admins can change it). The day resets at midnight Eastern.
  2. Database
    Remember. Loads what Nathan has learned about the asker (short notes, games to skip), what he suggested them in the last two weeks, and this chat so far: how it started plus the latest five turns.
  3. Gemini
    Understand. Turns the question into a plan: what kind of question it is (browse, recommend, person, game, buy, rules), who's playing, player count, time, weight, themes, games named. It starts on just the names of who's on the shelf while the whole shelf loads.
  4. Code
    Firm rules. These override the model's reading. "A game I don't own" means ideas to buy, "my" means the asker's shelf, "who has…" looks across friends, and "at Keith's" means Keith's shelf. "With my kids" is never a solo game and leaves out 13+ games until their ages are known; "they're 7 and 9" counts the kids plus the asker.
  5. Database
    Look things up. Finds the games named, even partial or misspelled names (match_game). Also gets who owns them, ideas to buy, friends' shelves, the asker's Top 10 and wishlist. For a rules question, the rulebook sections that best match its words, each with its document and page.
  6. BGG
    Fill the gaps. If a game isn't in our catalog yet, BoardGameGeek supplies it. The most-rated exact match wins.
  7. Code
    Shortlist. Applies the hard limits and scores the rest by the group's ratings, plays and taste. Follow-ups ("which of those are co-op?") stay within the last answer.
  8. Claude
    Nathan writes the answer from that shortlist only, in his voice: picks, reasons, a quip, and an honest note when nothing fits. In the same reply he notes up to two lasting facts the asker just told him ("has about an hour on weeknights"; code nudges him when the words say "I hate…", "I always…" or "burned out on…"), and, when one missing fact would change his pick, one short question back.
  9. Code
    Check the answer. Removes any game that wasn't on the shortlist, removes the asker's name used as a greeting, and drops a "worth a look" tip that names a game already owned. If he didn't ask, the two questions that matter most are added here: "How old are your kids?" and "How many of you are playing?" (never on a follow-up).
  10. Database
    Save it. After replying, saves the turn to the asker's chat history and applies what he learned (their notes, at most 30). The admin dashboard gets only the kind of question and how long it took, never the words.

The routes

Every address starts with https://api.ondorilabo.com/vault/ and needs a signed-in member. Each area has its own switch in Admin → Dashboard → New API (off, admins only, or everyone); photos and rulebook uploads are admins-only until Dan has tried them, everything else is on for everyone. n8n's old webhooks (https://n8n.ondorilabo.com/webhook/vault/) answer only if the API can't, until they're retired around October 30.

What runs on its own

Every night (Eastern)

All of it runs in the jobs worker (bgc-jobs, from server/bgc-api/src/jobs). Every run is written to the job_runs table, and GET /jobs on the worker lists each job's last run and next time.

4:30Sync every member's plays from their BGG account, Dan's included; anyone can also tap "Sync my plays" in the cog
4:50Sync people: the BGG ratings of everyone with a BGG username (who played with whom is kept up as plays arrive)
5:40Self-test: 82 database checks, then 37 real questions to Nathan, the memory ones included. Emails Dan only if something fails
9:00Health check: emails Dan if the database backup hasn't run in 26 hours
nightlyBackup: both databases dumped to the private GitHub repo (its own container)

All the time

  • Every 2 minutes: the rulebook reader picks up the next uploaded rulebook, if any (an upload also pokes it straight away). When it finishes one, a small call reads the first two pages to say what it is (the game's rulebook, an expansion's, an appendix…) and its name, filling only what was left blank.
  • Every 10 minutes: Fill Catalog gets BGG details and box art for 20 games that came in without them (wishlists and Top 10s first).
  • Every hour: records what the site's OpenRouter key has spent and the account balance, for Admin → Costs. Each AI call also records its own cost.
  • On request: a member's play import and a CSV import run as jobs the API hands over; if the worker is down, the API runs them itself.
  • On any failure: the worker emails Dan which job broke and where, once per job per half hour at most.

Never automatic

  • Release notes go to the testers' Discord only when Dan says so.
  • Nobody becomes a member without an invite from an admin or a friend code.

How a change ships

  1. Edit the sourceindex.html · app.js · admin.js · server/bgc-api/src · server/bgc-db/schema/NNN_*.sqlThe API still runs n8n's own code where the two overlap (Nathan's steps, input checks, BGG parsing): node server/bgc-api/scripts/extract-nathan.cjs copies it word for word from n8n/gen.js, until Nathan's fallback is retired. Rules that decide what's true (who may see or change what) go in SQL functions, not in routes.
  2. Apply database changesserver/bgc-db/schema/apply.shEach schema file is numbered (46 so far) and safe to run again; a ledger table records which have run. Bigger ones are tried first inside a transaction that's rolled back.
  3. Check, then deployserver/bgc-api/check.sh · deploy.sh (or --trial)Types, 75 tests and the build pass first. A trial build can answer Nathan's questions before it serves anyone. The new API container starts beside the old one and takes over only once it's healthy, so the site never blinks; then the jobs worker is recreated from the same image.
  4. Run the checksbgc.self_check(): 82 rules, rolled back afterwardsThe deploy fails if any check fails. It covers membership, privacy, ratings, wishlists, admin, game matching, rulebooks, Nathan's memory, and that every shelf is treated alike. node n8n/test-nathan.js asks the 37 Nathan questions; the worker asks them every night.
  5. Switch an area overAdmin → Dashboard → New APIA new area starts Off, then Admins only, then Everyone. The check there asks the API and n8n the same questions while both still answer.
  6. Push the pagegit push → GitHub Pages → node tools/purge-cache.jsOnce GitHub has published it, clearing Cloudflare's cache makes it live right away.
  7. Tell the testersCHANGELOG.md → node tools/post-update.js v0.22Posts that version's notes to the bgc-testers channel on Discord, only when Dan says so.

Where things are kept

In the database

  • members, friends: who's in, roles, friend codes, Top 10
  • games: the shared catalog, filled in from BGG
  • shelves: who owns what, favorites
  • plays, ratings: from BG Stats via BGG, and your stars
  • wishlist; rule_docs, rule_sections: the text Nathan read from each rulebook, by page (the PDFs themselves aren't kept)
  • chat_turns, member_notes: Nathan's memory. Chats are kept 6 months; notes stay until you delete them
  • ask_log, settings: question types and timings, limits, the last self-test, and the switches for which areas the API serves
  • job_runs: every run of every scheduled job, with its result or its error

Kept off the repo

  • The database password stays on the server (~/bgc-db/.env).
  • The API's and the worker's keys for OpenRouter, BGG and Resend (email) are in ~/bgc-db/.env on the server, placed there by Dan; n8n keeps its own as n8n credentials.
  • The server is reached only over SSH with a key, as a non-root user; its remote desktop relay (RustDesk) takes only clients that hold its key.
  • The Discord webhook is on Dan's PC (%USERPROFILE%\.bgc).
  • Chats are stored for Nathan's memory, and only the asker sees them. The admin dashboard shows question types, never the words.
